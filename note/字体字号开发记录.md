# 字体与字号里程碑开发记录

日期：2026-10-29。目标：Shell 字体换漂亮字体（Terminus）+ 字号三档可调（12/14/16 → 33/28/25 行）。

## 最终方案：纯 VGA 硬件编程（弃用 BIOS）

**SeaVGABIOS 没实现 INT 10h AX=1100h**（加载用户字体）：实测调用后平面 2 内容不变、CRTC 不重配、scanline 纹丝不动。改由内核直接编程 VGA：

- **写字体**（`font_write_plane2`）：SR4 bit2=1 关 odd/even 奇偶限制、GR5 写模式 0 + bit4=0、GR6 map=A0000 + bit1=0、SR2 Map Mask=0x04，然后写 0xA0000。**写模式 0 能直写数据的前提是 GR1 (Enable Set/Reset)=0**（文本模式默认）——GR1=0 时 set/reset 完全禁用，CPU 字节原样进平面。**★布局：每字形 32 字节步长**（`plane2[ch*32+row]`，先清零 8K 再写 h 行数据）——VGA 字符发生器取字形地址就是 ch*32+行号（QEMU `vga_draw_glyph9`: `font_ptr += 32*4*ch`，行循环 `+4`）。初版按连续 16 字节写，渲染出的字形 = 表内 `ch*2` 号字形，全屏乱码（见坑 4）。
- **CRTC 重配**（`font_set_crtc`）：CR09=h-1（行高）、CR12+CR07 bit1/bit6=rows*h-1（垂直显示结束）、CR0A/0B=h-2/h-1（光标）、CR14=h-1（下划线）。帧时序不动，换行高只是 400 线活动区里装 25/28/33 行。
- **自测**（`font_selftest`）：GR4 Read Map=2 从 A0000 按**同样的 32 字节步长**读回平面 2 与源数据逐字节比对 + 读 CRTC 验证。串口报 `[FONT] height=.. mismatch=.. scanline=.. vde=.. OK`。**教训：自测只保证"写入布局 == 读回布局"，布局本身错了它照样 OK（坑 4）——必须再加一道"渲染级"校验：截屏 + 字体模板 OCR 对比屏幕像素（本次用的方法）。**

**★VGA 索引寄存器陷阱（本里程碑最大坑）**：0x3C4/0x3CE 是粘性索引——每次写数据口（0x3C5/0x3CF）前必须重新选中目标索引。漏选时数据写进上一个索引的寄存器，症状是"读写结果完全不对但寄存器值看起来合理"。

**★文本模式平面寻址（QEMU vga.c 实测语义）**：
- 读：GR5 bit4=1 时平面 = (读映射&2)|地址bit0（odd/even 劫持）；GR6 bit1=1 时奇数地址被掩成偶数（每对字节读回同一个值 → mismatch 恰为一半！）
- 写：SR4 bit2=0 时写入被奇偶限制 + CR17 字模式下地址 >>= 1
- 写模式 1 = 写锁存器（`val = s->latch`），不是直写！写模式 0 + GR1=0 才是直写

## 挖出的三个旧内核 bug（与字体无关但被本里程碑触发/发现）

1. **跳板不保存 EBP/EBX/ESI/EDI** → SeaVGABIOS 处理 INT 10h 时短暂进 32 位保护模式随意用这些寄存器，返回后 C 函数经 `[ebp+N]` 访问局部变量 → 野指针（实测 font_apply 里 idiv 读到 h=0 → #DE → 三重故障复位循环，串口反复 "Paging ENABLED"）。旧代码没炸纯属运气（调用点从不访问局部变量）。**修复：rm_entry.asm 存/跳板 .flush 恢复 + cld**（DF 也可能被 BIOS 弄脏）。定位方法：QEMU `-d int -D log` 第一条异常 `v=00 e=0000 EAX=400` → objdump 找到 idiv。
2. **testmode 的"按任意键"等待**把回车释放码当"任意键"提前返回 → 真按键的按下码经 IRQ1 流进 shell 输入缓冲污染下一条命令（"font 12" 变 "afont 12"）。**修复：只接受按下码 (<0x80) + 等待后 kbd_drain() 再排空**。深层机制：触发命令的回车处理器还没 EOI，真按键的 IRQ1 在 PIC 挂起，轮询吃掉字节后 EOI 重投递 IRQ1，处理器读到**重复投递的按下码**（键盘打点实测 0x1E 出现两次）。
3. **mario 标题画面 "PRESS ANY KEY"**：ESC 也是"开始游戏"不是退出——测试流程必须 spc 进游戏再 ESC（非 bug，测试踩坑记录在案）。
4. **★font 切换/开机后屏幕持续乱码（2026-11-02 定位，真正根因）**：字体按连续 16 字节/字形写入平面 2，但 VGA 字符发生器按 **32 字节步长**取字形（`plane2[ch*32+row]`，QEMU 11.1.2 `vga_draw_glyph9` 实测/源码确认）→ 渲染出的字形 = 表内 `ch*2` 号字形，全屏乱码（'M' 0x4D 渲染成 0x9A）。**为什么一直没被发现**：① 文本缓冲区（0xB8000）内容永远正确，140 项测试全查缓冲区/串口，失明；② 平面 2 自测是自洽的——写入布局和读回布局都是连续布局，永远 OK；③ 历史截图本身就是乱码的，只验证了尺寸没验证字形。**定位方法**：QEMU monitor 读 0xB8000 确认缓冲区干净 → 排除逻辑层；screendump + 用 font16.h 字形做模板匹配 OCR 屏幕像素 → 发现渲染字形 = 2× 索引 → 对照 QEMU 源码 `vga_draw_glyph9` 的 `font_ptr += 32*4*ch` 确认步长。**修复：写入与自测都改 32 字节步长**（先清零 8K，每字形只写 h 行数据）。验证：12/14/16 三档字号 + 开机画面渲染级 OCR 全部 0 不匹配。（注：此前误以为 EOI 砸 EAX 是乱码根因——那是个真 bug 也会造成间歇性自测值错乱，但不是屏幕上持续乱码的原因，见抢占记录坑 3。）

## 字体数据来源

Terminus（专为终端设计的位图字体）：Arch 包 `terminus-font` → `ter-u12n/ter-u14n/ter-u16n.psf.gz`（PSF1 格式，宽度隐含 8；12 高度只有 6 宽窄体变种）。`tools/gen-font.py` 解析 PSF1/PSF2（含 Unicode 表）→ 生成 `kernel/font12.h` 等（256 字形 × height 字节，MSB=最左像素，与 VGA 字符发生器格式一致）。

## 测试基建教训（tools/test-font.py）

- QEMU stdio chardev 直接重定向到文件**被缓冲**，实时读不到 → 串口走管道 + 读线程
- BufferedReader.read(4096) 管道不足 4096 字节时**永久阻塞**（启动日志才 354B）→ 必须 os.read
- 测试脚本被 timeout 杀死会**孤儿化 QEMU** 持 os.img 写锁 → 后续 QEMU "Failed to get write lock" 假死 → 用 `-snapshot`（只读+内存覆盖，不拿锁）
- monitor xp 风暴冻结 VCPU（旧坑，见 tetris 记录）→ 退出信号用内核串口消息，BDA 只做一次确认
- 串口匹配串坑：`[Paging] ENABLED` 有方括号；serial_put_hex 是 8 位定宽（`0x00000010` 不是 `0x10`）
- 陈旧匹配：检查"基线之后的新数据"（serial_base 机制）
