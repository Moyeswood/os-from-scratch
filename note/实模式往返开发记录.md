# 实模式往返（Real Mode Round Trip）开发记录

> 日期：2026-10-28
> 状态：✅ 已完成并验证（`testmode` 命令可用）
> 对应提交：feat(realmode): 打通实模式往返

---

## 一、目标：为什么需要实模式往返？

NewOS 是 32 位保护模式内核。接下来的大目标是：

- 在 OS 里跑俄罗斯方块（`tetris/` 里已有 1435 行纯实模式汇编版，用 320×200×256 色图形模式）
- 以后写超级马里奥（同样需要图形模式）

**问题**：设置图形模式（如模式 13h = 320×200×256 色）只能通过 BIOS 的 INT 10h 完成，而 BIOS 服务是 16 位实模式代码，保护模式内核**不能直接调用**，原因有三：

1. **中断机制不同**：BIOS 靠 IVT（物理地址 0~0x400 的中断向量表），内核用的是自己建的 IDT
2. **PIC 已重映射**：`pic_remap()` 把 IRQ 挪到了 0x20 以上，BIOS 键盘中断（INT 9h）不再工作
3. **代码位宽不同**：BIOS 是 16 位代码，保护模式下无法执行

**方案**：需要时临时"降级"到实模式调 BIOS，用完再升回保护模式——这就是**实模式往返**。

## 二、核心设计：三个演员

### 为什么跳板必须在低内存（< 1MB）？

实模式 CS:IP 用 16 位偏移寻址，最大只能表示 0xFFFF。内核代码链接在 0x10000 以上，如果原地降级，高地址会被截断。早期 `realmode.asm`（现 realmode.asm.bak）就是犯了这个错：`mov eax, REAL16 / and eax, 0xFFFF` 把高地址截断成 16 位，跳过去就是乱码。

所以把一小段独立编译（`[ORG 0x6000]`）的二进制**拷贝到低内存 0x6000** 执行：

| 文件 | 角色 |
|---|---|
| `kernel/rm_trampoline.asm` | **跳板**本体：在低内存完成 降级 → INT 10h → 升级 |
| `kernel/rm_entry.asm` | **外壳**：32 位函数 `rm_switch_mode(mode)`，保存内核状态后送跳板出发 |
| `kernel/realmode.c/h` | **装载器**：`rm_load_trampoline()` 开机时把跳板二进制拷进 0x6000 |
| `kernel/rm_embed.asm` | 把跳板二进制 incbin 进内核镜像（编译期嵌入） |

### 内存布局图

```
物理地址          内容
─────────────────────────────────────────────
0x0000 ~ 0x0400   IVT (BIOS 中断向量表, 不能碰)
0x0400 ~ 0x0500   BDA (BIOS 数据区, 不能碰)
0x0500            boot.asm 存的扩展内存大小
0x0580 ~ 0x058B   boot.asm 保存的 BIOS GDTR/IDTR  ★关键★
0x0600            boot.asm 存的启动盘号
0x5400 ~ 0x541A   内核保存区 (GDTR/CR3/返回地址/ESP/模式号/IDTR)
0x5FF0            实模式栈顶 (向下生长)
0x6000 ~ 0x6200   跳板 (GDT 在 0x6020, 入口在 0x6100)
0x7000            ⚠️ SeaBIOS 实模式栈 (向下生长, 放东西会被踩)
0x7C00            引导扇区 (内核 GDT 在 0x7DA0 附近, GDTR 一直指向它)
0x10000+          内核
```

保存区布局（0x5400，rm_entry.asm 写入 / rm_trampoline.asm 读取）：

| 地址 | 内容 |
|---|---|
| 0x5400 | 内核 GDTR (6 字节) |
| 0x5406 | 内核 CR3（页目录） |
| 0x540A | 返回地址（跳板最后 `jmp dword [0x540A]` 回到这里） |
| 0x540E | 内核 ESP |
| 0x5412 | 请求的视频模式号（INT 10h 参数） |
| 0x5414 | 内核 IDTR (6 字节) |

### 完整流程（串口打点 A~G 对应）

```
shell: testmode 命令
  → rm_switch_mode(0x13)            [rm_entry.asm]
      cli                          ← 全程关中断, 任何 IRQ 不打扰
  A   sgdt/sidt 保存内核 GDT/IDT, 存 CR3/ESP/返回地址/模式号
      关分页 (清 CR0.PG)
  B   lgdt [0x6000]                ← 加载跳板自己的 GDT
      jmp 0x18:0x6100              ← 远跳进 16 位代码段
  C   entry16: 设 16 位段, 清 CR0.PE → 正式进入实模式
  D   real_entry: 段寄存器归零, 栈 0x5FF0
      lgdt [0x580] / lidt [0x586]  ★ 恢复 BIOS 的 GDT/IDT ★
      INT 10h AX=0x0013            ← BIOS 切 320x200x256 图形模式
  E   BIOS 返回
      lgdt [0x6000]                ← 换回跳板 GDT
      A20 保险重开, 置 CR0.PE
      jmp 0x08:entry32             ← 跳进 32 位代码段
  F   entry32: 32 位段, lgdt [0x5400] 恢复内核 GDT, lidt [0x5414] 恢复内核 IDT
  G   jmp 0x08:.reload 刷新 CS → 恢复 CR3 + 重开分页 → 恢复 ESP → sti
      jmp dword [0x540A]           ← 回到 shell.c 里调用点, 对 C 来说就是普通函数返回
  → C 代码画测试图案 → 等按键 → 第二次往返切回 0x03 文本模式
```

## 三、踩过的坑（按时间顺序）

### 坑 1：GDT 描述符写成 9 字节（旧代码遗留 bug）

**现象**：串口打点停在 `AB`，`C` 永远不出现，随后内核重启（三重故障 → CPU 复位，串口日志里出现两遍启动信息）。

**定位**：`objdump -D -b binary` 反汇编跳板二进制，发现 `gdt_ptr` 里的 limit = 43（应该是 39）。每个描述符多了 1 字节。

**根因**：旧 rm_trampoline.asm 写的是

```asm
dw 0xFFFF, 0x0000, 0x00        ; ← 三个字 = 6 字节！
db 10011010b, 11001111b, 0x00
```

段描述符必须是 8 字节：limit低16 + base低16 + base中8 + 访问字节 + limit高4/标志 + base高8。多出来的一个字把整个 GDT 字段错位，加载选择子 0x18 时读到垃圾描述符 → #GP → 双重故障 → 三重故障 → 重启。

**修复**：

```asm
dw 0xFFFF
dw 0x0000
db 0x00
db 10011010b, 11001111b, 0x00
```

**教训**：GDT 描述符是位域结构，多一个字节全表错位；旧文件里的"看起来差不多"的写法要逐字节核对。

### 坑 2：entry16 没对齐 0x6100

**现象**：同样停在 `AB`（这次 GDT 已修好），还是进不了跳板。

**定位**：反汇编发现 0x6100 处是 `marker` 调试函数而不是入口代码。

**根因**：NASM 按文件顺序排代码，我把 `marker` 函数写在了 `entry16` **前面**，它占掉了 0x6100 的位置，真正的入口被挤到 0x610F。外壳 `jmp 0x18:0x6100` 正好跳进 marker 函数中间。

**修复**：把 `marker` 挪到文件末尾（16 位代码 near call 在 64KB 段内随便放）。

**教训**：`[ORG]` + `times 填充` 布局的代码，**第一个跟在填充后面的标签就是入口**，任何辅助代码都要放后面。

### 坑 3：没恢复 BIOS 的 GDTR/IDTR ★最大的坑★

**现象**：打点走到 `ABCD`，`E`（INT 10h 返回后）永远不出现，系统挂死。QEMU monitor 查寄存器：CPU 卡在 `CS:IP = 0000:0002`（物理地址 0 的 IVT 字节被当成代码执行），SS=0x00C4 野值；查内存：IVT（0x0~0x400）和 BDA 被整片覆盖成垃圾模式（如 `44 00 03 00` 重复出现）。

**定位过程**（这一坑花的时间最长）：

1. 隔离测试：写了一个不进保护模式的独立引导程序（同样的栈 0x5FF0 + 同样的 PIC 重映射），INT 10h **完全正常** → 说明 PIC 重映射和栈不是问题
2. 对比 IVT：干净启动 vs NewOS 启动后，IVT 完全一样（INT 10h = C000:4E9F 指向 VGABIOS）→ IVT 没被内核破坏
3. `xp` 反汇编 VGABIOS 入口（C000:4E9F）：`test byte [0x4B9], 0x40; jz fast_path` 分支选择、`mov ss, [cs:0x8d38]` 切换自己的栈——这些都是正常行为
4. GDB 单步 + 硬件监视点尝试：QEMU 11.1.2 的 gdbstub 监视点触发时自己 BQL 崩溃；单步在实模式会误报（EIP 显示 0,1,3 死循环是假象）→ 放弃 GDB 路线
5. 关键推理：挂死时的垃圾数据 `83 00 23 00 ... 07` 是 **BIOS 风格的 IDT 表项格式**（RPL=3 选择子）→ BIOS 自己的表被写到了错误的地方 → BIOS 在按错误的 GDT/IDT 运行

**根因**：**SeaVGABIOS 设置视频模式时会短暂进入保护模式**，用的是**当前 GDTR/IDTR 指向的表**。我们的跳板在降级前把 GDTR 换成了跳板自己的 GDT（IDTR 还是内核的 IDT），BIOS 一进保护模式，段选择子和中断门全部错位，在内存里乱写（把 IVT/BDA 覆盖成垃圾）后挂死。

**修复**：`boot.asm` 在进保护模式前用 `sgdt [0x580] / sidt [0x586]` 保存 BIOS 的 GDTR/IDTR；跳板在调 INT 10h **之前** `lgdt [0x580] / lidt [0x586]` 恢复 BIOS 的表；INT 10h 返回后换回跳板 GDT 升回保护模式；entry32 里恢复内核的 GDTR/IDTR（**不恢复内核 IDTR 的话，回内核开中断后 IRQ1 会走 BIOS 的 IDT = 崩溃**）。

**教训**：这是 OSDev 的经典坑——调 BIOS 不只是"切回实模式"，BIOS 内部随时可能再进保护模式，**它看到的 GDTR/IDTR 必须是它自己的**。

### 坑 4：保存区放 0x6E00 被 SeaBIOS 栈踩

**现象**：早期版本保存区放 0x6E00，状态莫名损坏。

**根因**：SeaBIOS 在实模式里的**内部栈在物理地址 0x7000（向下生长）**，INT 10h 调用期间会压到 0x6E00 一带，把保存区踩坏。

**修复**：保存区挪到 0x5400（远离 BIOS 栈 0x7000 和跳板 0x6000）。

**教训**：低内存 0x500~0x8000 是 BIOS 的自留地，放数据前要查清楚 BIOS 用哪些区域（SeaBIOS 栈 = 0x7000 向下；VGABIOS 保存区 = 0x5D0~0x5FC）。

### 坑 5：8042 缓冲区残留——回车释放码被误当成"按任意键"

**现象**：往返本身全通了（打点 A~G 齐），但图形模式**一闪而过**——BDA 视频模式字节在 t+1s 时已是 0x03，串口显示整个流程 1 秒内跑完。

**定位**：monitor 每 1 秒采样 BDA[0x449] + 串口日志时间线，发现"等待按键"阶段被瞬间跳过。

**根因**：回车键的**按下码**（0x1C）触发 IRQ → shell 执行 testmode 命令；而它的**释放码**（0x9C）晚到，留在 8042 输出缓冲区里。测试程序里"按任意键返回"的轮询循环 `while (!(inb(0x64) & 1))` 一进去就看到这个残留字节，立刻切回文本模式。第一次修复（进入等待前清空一次缓冲区）不够——因为释放码**比清空动作更晚到达**，存在竞态。

**修复**：循环清空直到缓冲区安静：

```c
do {
    while (inb(0x64) & 1) { inb(0x60); }           // 清空 8042 输出缓冲区
    for (volatile int i = 0; i < 20000000; i++);   // 给晚到的释放码留到达时间
} while (inb(0x64) & 1);                           // 又来字节就再清一轮
while (!(inb(0x64) & 1)) { }                       // 现在等的才是新鲜按键
inb(0x60);
```

**教训**：8042 输出缓冲区只有 1 字节；按键是"按下+释放"两个事件，**触发命令的那个键的释放码一定会晚到**。任何"等按键"逻辑都要先排空缓冲区并留出释放码到达的时间窗。

## 四、调试方法总结（以后都能复用）

| 工具 | 用途 | 注意 |
|---|---|---|
| 串口打点 A~G | 定位崩溃/挂死在哪个环节 | 全程 cli 期间也能打，比 GDB 可靠 |
| QEMU monitor `sendkey` | 通过 unix socket 向虚拟机注入按键 | 每次注入按下+释放一对事件 |
| QEMU monitor `xp` | 直读物理内存：BDA(0x449 模式字节)、IVT、帧缓冲 0xA0000 | 无头模式下验证图形内容**唯一可靠手段** |
| `info registers` | 挂死时看 CPU 停在哪儿 | 挂死场景比崩溃场景好用 |
| `-serial stdio` 重定向 | 实时观察串口时间线 | `-serial file:` 有缓冲丢失问题 |
| objdump/ndisasm | 验证跳板二进制布局和编码 | 二进制布局 bug 靠它一眼看出 |
| 隔离引导程序 | 二分定位：把可疑差异逐项复现 | 本次靠它排除了 PIC/栈/IF 的嫌疑 |

**已探明的工具陷阱**：
- `-display none` 时 QEMU 不更新显示表面，`screendump` 出来是全黑；且输出是 **PPM**（`file` 说 Netpbm）不是 PNG，要 `magick` 转换
- QEMU 11.1.2 gdbstub：硬件监视点触发时 QEMU 自己 BQL 断言崩溃；实模式单步 EIP 误报（显示 0,1,3 循环是假象）
- QEMU 用 `-drive format=raw` 启动这镜像不起动，要用 `-fda`（软盘）

## 五、验证结果（2026-10-28）

时间线采样（monitor 每 1s 一次）：

```
t+1s ~ t+4s:  BDA[0x449] = 0x13  （图形模式持续保持, 在等按键）
spc 后:       BDA[0x449] = 0x03  （文本模式恢复）
```

帧缓冲 0xA0000 内容（图形模式期间）与 `gfx_test_pattern()` 预期完全一致：

```
行 0  : 0f 0f 0f ...   (白色上边框)
行 40 : 0f 02 02 02... (橙, (x/40+y/40)%8+1 = 2)
行 80 : 0f 03 03 03... (黄)
行 199: 0f 0f 0f ...   (白色下边框)
```

串口完整打点：`ABCDEFG` × 2（去程和回程）+ `[RM]` 阶段消息全齐。
