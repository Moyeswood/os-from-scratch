# 里程碑 14：可执行文件加载与进程替换

日期：2026-11-06

## 1. 目标

里程碑 13 已经让每个用户进程拥有独立、按需分配的虚拟地址空间，但所有
程序仍然直接来自内核里的 `incbin` 表。进程也没有办法在不结束自己的
情况下换掉整个程序映像。

里程碑 14 增加：

```text
/bin 可执行文件发布
  → 从内存文件系统读取 flat 镜像
  → 校验路径、文件大小和读取完整性
  → 创建全新的进程地址空间
  → 成功时原地切换 CR3 并保留 PID
  → 失败时保留旧地址空间，返回 -1
```

最终 Shell 可以执行：

```text
run /bin/hello
run execdemo
run execbad
```

## 2. 为什么还需要加载器

内嵌程序表解决了“内核如何携带用户程序”的问题，却没有解决普通 OS 的
基本模型：可执行文件应当独立于进程，并且可以被重复加载。

从文件加载后：

- 同一路径可被多次启动；
- 文件系统成为程序来源；
- 内核不再要求所有程序都在编译期进入程序表；
- `exec` 可以复用同一个镜像加载流程；
- 临时加载缓冲区在镜像复制完成后立即释放。

## 3. `/bin` 的启动发布

文件系统在 `user_init()` 之前已经初始化。程序表初始化完成后，
`exec_install_builtins()` 会：

1. 创建 `/bin` 目录；
2. 遍历 `user_progs`；
3. 创建 `/bin/<name>`；
4. 把对应的 flat 镜像写入文件；
5. 输出安装统计：

```text
[EXEC] installed 0x0000000C/0x0000000C programs in /bin
```

这一步仍使用内嵌镜像作为“安装介质”，但运行路径已经改为真实文件内容。
以后替换成磁盘镜像或块设备时，只需要替换安装来源。

文件系统单文件上限是 48KB，用户镜像上限仍是 256KB。因此当前实际可由
文件系统加载的镜像受 48KB 限制。

## 4. 获取文件大小

加载器不能在不知道大小的情况下安全分配缓冲区。`fs_size(path)`：

- 查找 inode；
- 拒绝目录、缺失文件和非法路径；
- 返回文件字节数。

加载流程：

```text
fs_size(path)
  → kmalloc(file_size)
  → fs_read(inode, buffer, 0, file_size)
  → 要求读取字节数完全等于文件大小
```

任何一步失败都会释放缓冲区，并保留当前进程。

## 5. Flat 镜像约定

当前用户程序仍用自定义链接脚本链接到 `0x02000000`，再通过
`objcopy -O binary` 生成 flat 镜像。

文件内容按页装入：

```text
0x02000000  _start
0x02000xxx  代码 / 只读数据 / 数据
最后不足一页 → 清零补齐
```

加载完成后：

```text
EIP     = 0x02000000
USER_ESP = 0x02400000
CS      = 0x1B
SS      = 0x23
```

用户栈页仍然由首次调用/写栈触发 #PF 后分配。

## 6. 从文件启动新进程

`run /bin/hello` 与内嵌 `run hello` 共用进程创建骨架：

```text
proc_spawn_file(path)
  → exec_load_file
  → proc build_process(name, image, size)
  → vm_init_image
  → Ring 3 初始帧
  → READY
  → 前台 proc_wait / 后台立即返回
```

程序名从路径最后一段提取，因此 `ps` 显示的是 `hello`，而不是完整路径。

## 7. exec 的事务语义

`SYS_EXEC` 接收一个用户态路径指针。系统调用入口先逐页验证并复制最多
`FS_PATH_MAX` 字节到内核栈，避免内核直接解引用恶意地址。

随后 `exec_replace_current()`：

1. 从文件系统读取新镜像；
2. 在单独的任务描述中调用 `vm_init_image()`；
3. 如果页目录、页表或页分配失败，销毁临时地址空间并返回 -1；
4. 新地址空间完整后，切换 CR3；
5. 更新当前 PCB 的 `cr3/image_end/brk/mmap_brk`；
6. 销毁旧地址空间；
7. 释放临时文件缓冲区；
8. 改写当前 `int 0x80` 返回帧，直接 `iret` 到新程序入口。

这个顺序保证 `exec` 失败时旧程序仍然完整可运行。`execbad` 专门验证
缺文件和非法路径指针两条失败路径。

PID 保持不变：

```text
[EXEC] replace pid=0x00000005 old_pd=... new_pd=... path=/bin/hello
```

父进程关系、任务槽和调度状态也不会被重新创建。

## 8. CR3 切换顺序

不能在仍使用旧 CR3 时释放旧页目录。正确顺序必须是：

```text
创建新地址空间
  → 写入 CR3
  → TLB 随 CR3 重载刷新
  → 更新 PCB
  → 释放旧地址空间
```

内核恒等映射 PDE 0..7 在旧、新页目录中相同，因此切换 CR3 后，当前内核
代码、栈和串口输出都仍然可访问。

旧地址空间可能仍被 fork 子进程共享。销毁时只减少共享页引用计数，
有子进程使用的页不会被提前释放。

## 9. 中断状态修复

里程碑 13 的 `vm_destroy/vm_clone/vm_brk` 曾直接执行 `sti`。在普通内核
任务里问题不明显，但 `exec` 运行在 `int 0x80` 路径中；无条件开中断会
允许调度器在系统调用尚未完成时切走。

里程碑 14 改用保存/恢复 IF：

```c
flags = irq_save_disable();
...
irq_restore(flags);
```

原上下文关中断时，函数结束仍保持关中断；只有原上下文允许中断时才恢复
`sti`。

## 10. 代码位置

- `kernel/exec.c/h`：文件加载、`/bin` 发布、当前进程替换。
- `kernel/proc.c`：内嵌镜像与文件镜像共用的进程创建路径。
- `kernel/user.c`：`SYS_EXEC`、用户路径复制、`run <path>`。
- `kernel/fs.c/h`：新增 `fs_size()`。
- `user/execdemo.c`：成功执行 `exec("/bin/hello")`。
- `user/execbad.c`：验证缺文件和非法指针不会破坏旧进程。

- `run /bin/hello` 触发文件读取并执行；

- `execdemo` 加载 `/bin/hello`；
- PID 保持不变；
- 页目录确实从 old_pd 切换到 new_pd；

- 缺文件时返回 `-1`；

- 原有内嵌 `run hello` 兼容；
- 所有临时进程退出后 managed page 数回到基线。

## 12. 当前限制

- 格式仍是固定基址 flat binary，不是 ELF。
- 没有 `argv`、环境变量和辅助向量。
- 没有 shebang、权限位和可执行位。
- 文件系统局限为内存 FS，单文件最大 48KB。
- 外部输入文件没有格式 magic；错误镜像只会导致该用户进程异常，
  不会获得内核权限。

下一阶段的自然方向：

```text
ELF32 program headers
  → argv/envp 初始栈
  → 文件打开/读取系统调用
  → 用户态 shell
  → 管道与重定向
```
